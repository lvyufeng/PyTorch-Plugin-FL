## Summary

Vendor and boxing confs were sparse, so "op absent from the file" and "op known to have
no accelerated implementation" were indistinguishable. Operator support could not be
counted from a conf, and sparse files rotted silently against a growing codegen. This PR
converts five confs to one full-coverage shape: all 2036 routable ops listed exactly
once under `flaggems_cpp` / `flaggems` / `tileops` / `<vendor>` / `none`, generated by
`scripts/gen_vendor_confs.py`. Native-vendor platforms gain FlagGems-first routing;
the two boxing confs keep a byte-identical per-op key distribution.

`torch_fl/configs/` now contains exactly one `backends_<platform>.conf` per platform and
nothing else. Three files there — `backends_flaggems.conf`, `backends_flaggems_cpp.conf`
and `backends_tileops.conf` — routed nothing on their own; they were coverage *data* that
the generator read, plus (for tileops) a whole-table override selected by an env var. They
are now `frozenset` constants in `scripts/backend_coverage.py`, and the tileops override
became a per-op `# tileops` annotation applied at load time.

Each conf is bounded by that platform's real registration set, read from the generated
`*_register.inc` files `csrc/aten/register.cc` includes. FlagGems coverage is measured on
CUDA and is only a ceiling: the FlagGems wrapper is reached *through* an op's PrivateUse1
registration, so routing an unregistered op to `flaggems` would name a kernel no call
arrives at while the file reported it as covered.

**No route was measured on hardware.** See Verification — this is a shape-and-routing
refactor validated by regeneration, not by device runs.

## Problem Analysis

### What was broken/missing?

Only 7 FlagGems ops were active on MUSA, and reaching even those required
`FLAGOS_USE_FLAGGEMS=1`. The default `backends_musa.conf` had zero FlagGems entries.

The general defect is worse than one platform's count. A sparse conf cannot express
"this platform has no accelerated implementation for this op" — that state is encoded by
omission, which is the same encoding as "nobody has updated this file yet". Two
consequences:

1. Operator support is not countable. You cannot read a conf and say how many ops a
   platform accelerates, because the absent ones are unclassified.
2. A sparse conf silently rots against codegen. The Ascend baseline grew to 223 ops via
   codegen while the hand-maintained hybrid conf stayed at 55. The 168 ops in between
   fell through to `Backend::kFlagOs`, which has no kernel registered in an Ascend build,
   surfacing at runtime as `<op>: backend not registered`.

### Why did it happen?

`_select_backend_config()` mapped a platform marker to a sparse default and reserved the
FlagGems-bearing conf behind an env var. That was correct when the vendor conf was
mudnn-only and FlagGems was experimental, and it silently stopped being correct once
FlagGems became the preferred path. Nothing enforced the relationship between the
conf, the codegen op list, and the registered dispatcher slots, so the three drifted.

### Investigation process:

1. Traced the 7-op count to `_select_backend_config()` and the `FLAGOS_USE_FLAGGEMS`
   gate, confirming the default conf had no FlagGems entries.
2. Read `csrc/aten/register.cc:430-475` to establish the registration contract: claiming
   an op on PrivateUse1 without a kernel yields `backend not registered`, while leaving
   it unregistered reaches `cpu_fallback`. This is what makes `none` meaningful as an
   explicit value rather than a synonym for omission.
3. Diffed each platform conf against `backends_cuda.conf` (the authoritative codegen
   enumeration) and found the Ascend 223-vs-55 gap described above.
4. Compared the boxing confs against the vendor confs and found they encoded the same
   three concepts with a different vocabulary and no `none` — hence one generator with a
   `cuda` fallback slot rather than two schemes.
5. Grepped `csrc/aten/backends/flagos/python_op_caller.cc` for a FlagGems import-failure
   fallback and found none (only `TORCH_CHECK` on type/shape at 173, 278, 571, 596, 640).
   Routing an op to a FlagGems path that cannot import therefore raises rather than
   degrading — which is why the `flaggems_cpp` build gate below is load-bearing.

## Solution Design

### Implementation approach:

`scripts/gen_vendor_confs.py` generates five confs from `backends_cuda.conf` (the op list),
the coverage sets in `scripts/backend_coverage.py`, each platform's registration set read
from the generated `*_register.inc` files, plus each boxing platform's existing conf for its
own measured facts. Priority is `flaggems_cpp > flaggems > tileops > <vendor> > none`.

### Key design decisions:

**Five keys, with `none` explicit.** `none` is the whole point of the full-coverage
shape: it turns an unclassified absence into a stated verdict, which is what makes
support countable and rot detectable. Omission is not even a safe way to say
"unsupported" — `GetBackendForOp()` returns `kFlagOs` on a table miss, so an unlisted op
claims a FlagGems kernel by default.

**`tileops` is a routing key, not a conf.** `FLAGOS_USE_TILEOPS=1` used to swap the whole
table for `backends_tileops.conf`, a third full copy of the op list whose only real content
was 60 `tileops` entries. It is now a trailing `# tileops` annotation on those ops in
`backends_cuda.conf`, and `ApplyTileOpsOptIn()` in `common.cc` repins them at load time
using the same `alt` map `ALL_USE_*` already parses. That keeps the per-op default and the
TileOPs candidate on one line, and it means the flag composes with the rest of the file
instead of replacing it. `TILEOPS_PLATFORMS` is empty, so no *generated* conf spells the
key: `setup.py` forces `TILEOPS_KERNEL=OFF` for every non-CUDA accelerator, where
`kTileOps` would degrade to an equally empty `cuda_fn_`.

**A conf may not claim more than the platform registers.** This is the load-bearing
invariant. Registration sets come from the generated `*_register.inc` files that
`csrc/aten/register.cc` includes — the same list the compiler sees — so `route()` returns
`none` for any op outside them regardless of FlagGems coverage. Measured result:

| platform | registered | `flaggems` | `<vendor>` | `none` |
|---|---|---|---|---|
| ascend | 374 | 248 | 126 | 1662 |
| gcu | 152 | 88 | 64 | 1884 |
| musa | 158 | 122 | 36 | 1878 |

`test_vendor_routing_never_exceeds_registration` pins this as **equality**, not just
containment, so it also catches the converse: a registered op left at `none` would send a
real kernel to `cpu_fallback`.

**That bound decides which platforms get a generated conf.** A `none` entry boxes to
`cpu_fallback` only where registration *skips* the op. metax, tsingmicro and dcu fall
through to the `#else` branch in `register.cc` and claim the full generated list, so `none`
there would reach the dispatcher and raise on an empty slot instead of falling back. Only
musa, gcu and ascend are generated as native-kernel vendors; metax is covered by its
single boxing conf (`backends_metax.conf`), and `backends_tsingmicro.conf` stays
hand-written and sparse.

**Ascend goes through its code generator, per CLAUDE.md.** `codegen_ascend.py` now emits
an `m.impl()` subset naming only its 286-entry coverage set, instead of `register.cc`
including the full ~2036-op `generated/register.inc` for Ascend. `matmul` and
`matmul_backward` stay claimed directly from `register.cc` under `#if defined(USE_ASCEND)`
so the call hits fused `aclnnMatmul` rather than decomposing; the generator carries them as
explicit native extras because `WrapperMatmul` reads this conf to decide.

**Boxing platforms use the same generator.** The fallback slot is spelled `cuda`, so a
boxing conf has no `none` entries — boxing reuses the CUDA kernels for every op. The
difference from a native vendor is coverage, not shape.

**For boxing platforms the generator reads the file it rewrites, so measured facts must
survive a round trip.** Two sets could plausibly be re-derived from shared sources, and
re-deriving either would silently reroute working kernels:

- Each boxing platform's triton gap set — an op FlagGems covers that this platform must
  keep on `cuda` (MetaX Xnack/ATU faults, DCU hcu VMFault, missing `div_rn` lowering).
  Recovered by diffing the conf against the coverage sets, so the per-op
  diagnosis stays in `codegen_ops.py` and is not restated in two places.
- MetaX's FlagGems-C++ subset, which is **not** the shared `fg_cpp` set:
  the measured 17-of-18 on-device set (in `METAX_CPP_MEASURED` in the generator)
  deliberately keeps `mm` boxed. Re-deriving would promote `mm` silently.

**`flaggems_cpp` is emitted only in `backends_metax.conf` (when `FLAGGEMS_KERNEL=ON`).** That slot is
`Backend::kFlagOs`, registered behind `#ifdef FLAGOS_FLAGGEMS_CPP`, which is defined only
for a `FLAGGEMS_KERNEL=ON` build; `CMakeLists.txt` force-sets it `OFF` for ascend, dcu,
musa, bpu, and tsingmicro. When `FLAGGEMS_KERNEL=OFF`, the 15 `flaggems_cpp` entries in
`backends_metax.conf` degrade safely: `Dispatcher::GetFn` for `kFlagOs` falls back to
`cuda_fn_` when `flagos_fn_` is empty, so those ops take the boxing path with no error.
No coverage is lost: the C++ op set is a subset of the Python set, so those ops use the
same FlagGems kernels via the boxing path and only the GIL-free entry point is given up.

**`ALL_USE_*` refuses to reroute to a nonexistent kernel.** `ALL_USE_FLAGGEMS=1` and
`ALL_USE_VENDOR=1` collapse the table for A/B measurement and are mutually exclusive
(both set: warn, ignore both). An op moves only when its routed value or its annotation
proves that backend implements it. The rest are reported on stderr and left as
configured. Silently rerouting would surface much later as `backend not registered`
mid-model, which is exactly the failure mode this PR exists to remove.

**A vendor kernel that loses to FlagGems is still recorded.** A line FlagGems wins by
priority carries a trailing `# <vendor>` annotation, so the conf remembers that a kernel
exists behind the op. Without it a later FlagGems regression could not be routed back to a
kernel that does exist, and `ALL_USE_VENDOR` would have nothing to prove the kernel by.

## Performance Impact

No intended change. One relevant detail: `Dispatcher::operator()` memoizes the resolved
backend per op, because constructing a `std::string` and hashing it in `BackendTable` on
every op call measured as significant in the Ascend eager decode loop (thousands of ops
per token). The cache is `mutable` and benign under a concurrent first call — all threads
compute the same immutable value.

Native platforms now route many ops to FlagGems that previously reached `cpu_fallback`.
That is expected to be faster, but it is **unmeasured** on hardware.

## Breaking Changes

**⚠️ This PR contains breaking changes**

### What breaks:

1. **Conf vocabulary.** `flaggems` previously meant the C++ slot; it now means the
   Python slot, and the C++ slot is `flaggems_cpp`. A **stale `libtorch_fl.so` paired
   with a new conf misroutes**, and vice versa. The legacy spellings `flagos`,
   `flaggems_python` and `flagos_python` remain accepted so an out-of-tree conf or a
   pinned script keeps working, but `flaggems` itself changed meaning and cannot be
   aliased both ways.
2. **Deleted confs.** `backends_{ascend,metax,musa}_flagos_py.conf` are gone, and so are
   `backends_flaggems.conf`, `backends_flaggems_cpp.conf` and `backends_tileops.conf`.
   Anything pointing `FLAGOS_BACKEND_CONFIG` at one of those paths will fail to open it.
   The last three were never platform confs — no platform selected them — so pointing a
   run at one produced a table whose vendor key matched no compiled backend.
3. **Retired env vars.** `FLAGOS_USE_FLAGGEMS`, `FLAGOS_USE_VENDOR_OPS` no longer decide
   anything. They are ignored, not errors. `ALL_USE_FLAGGEMS` / `ALL_USE_VENDOR` are the
   supported way to collapse routing. `FLAGOS_USE_FLAGGEMS_CPP` is also gone: it selected
   a conf whose only difference from the platform conf was a set every generated conf now
   carries on its own.
4. **`FLAGOS_USE_TILEOPS=1` changed mechanism, not meaning.** It used to replace the whole
   table with `backends_tileops.conf`; it now repins the 60 annotated ops in place. The
   observable difference is that the other ~1976 ops keep the platform's own routing
   instead of silently reverting to whatever the tileops conf happened to say, and the
   opt-in now yields to `ALL_USE_FLAGGEMS` / `ALL_USE_VENDOR` with a message on stderr
   rather than fighting them.

### Migration path:

```
# Old: opt into FlagGems on a native vendor
FLAGOS_USE_FLAGGEMS=1 python train.py

# New: FlagGems-first is the default; no env var needed
python train.py

# Old: hand-written conf using `flaggems` for the C++ runtime
mm = flaggems
# New: say which path you mean
mm = flaggems_cpp   # C++ runtime (liboperators.so)
mm = flaggems       # Python/Triton path

# Old: point the config at a shared conf to get the tileops table
FLAGOS_BACKEND_CONFIG=torch_fl/configs/backends_tileops.conf python train.py
# New: the opt-in repins the annotated ops in the platform's own table
FLAGOS_USE_TILEOPS=1 python train.py
```

### Affected users:

Anyone with a hand-maintained out-of-tree conf, a pinned `FLAGOS_BACKEND_CONFIG` path, or
a mixed-vintage install where `libtorch_fl.so` and the confs come from different builds.
Rebuild so both sides share the vocabulary.

### Edge Cases Considered

1. **Vendor-only ops absent from the CUDA op list** — Ascend `matmul` and
   `matmul_backward`. Dropping them would un-route a working kernel, so the op list is
   widened by the union and the addition is printed. A test pins that every platform ends up
   with an identical op set, since coverage counts are otherwise incomparable across files.
2. **An op the vendor implements that FlagGems also covers** — routed to FlagGems by
   priority, kernel preserved via the `# <vendor>` annotation. Tested in both
   `flaggems_cpp` and `flaggems` positions.
3. **A triton gap on an op FlagGems covers** — the measured gap outranks coverage for
   that platform; tested that `route_boxing` returns `cuda` in that case.
4. **Both `ALL_USE_*` set at once** — warn and ignore both rather than pick one.
5. **An op with no implementation on either candidate under `ALL_USE_*`** — reported on
   stderr, left as configured, never pointed at an empty slot.
6. **A conf routing to `none` for an op that is nonetheless registered** — `GetFn`
   returns nullptr and the error names the real cause (regenerate the conf so
   registration and routing agree) instead of the misleading "backend not registered".
7. **`kTileOps` with an empty slot** — TileOPs kernels are bound in Python via
   `torch.library` and normally intercept earlier; a conf entry reaching the dispatcher
   means that registration did not happen, so it falls back rather than hard-failing.
8. **Cyclic or deep `include`** — depth capped at 8 with a warning, so a bad conf cannot
   hang import.
9. **`ruff format` idempotency on the generated confs** — not applicable, but the
   generator's own output is byte-stable, which the idempotency test enforces.

### Potential Risks

1. **Unmeasured native routing.** Hundreds of ops per platform move from `cpu_fallback`
   to FlagGems with no on-device validation. A FlagGems kernel that is wrong or absent on
   a given accelerator will now be reached where previously it was not. This is the main
   risk and the reason the doc marks every row not revalidated.
2. **Vocabulary skew between a stale `.so` and a new conf** silently misroutes rather
   than failing loudly, because both spellings parse.
3. **`flaggems_cpp` gating depends on `CMakeLists.txt` staying in sync.** If a platform
   is later built with `FLAGGEMS_KERNEL=ON`, its conf should be regenerated to take
   advantage of the C++ path; nothing currently detects that.

### Rollback Plan

`git revert` this commit. The confs are generated artifacts, so the revert restores the
previous files exactly; no state migration is involved. The C++ parser change reverts
with them, keeping the `.so` and the confs on the same vocabulary. If only the routing is
at fault but the shape is wanted, `FLAGOS_BACKEND_CONFIG` can point at an older conf, or
individual ops can be pinned with `FLAGOS_OP_<name>=<backend>`.

## Human Review Notes

### Areas needing special attention:

1. **The `flaggems` semantic flip in `csrc/aten/common.cc:106-116`.** This is the one
   change that can silently misroute a mixed-vintage install. Confirm the build/packaging
   story keeps the `.so` and the confs together.
2. **`ApplyTileOpsOptIn()` at `csrc/aten/common.cc:313-333`.** It reads the same `alt` map
   `ALL_USE_*` parses, so a `# tileops` annotation is now load-bearing rather than a
   comment. Worth confirming the yield-to-`ALL_USE_*` precedence is the one you want: the
   alternative is letting the opt-in win, which would leave 60 ops off the backend being
   measured.
3. **Whether the native platforms should ship FlagGems-first unvalidated.** This is a
   judgment call about risk appetite that I cannot settle without the hardware. The
   alternative is landing the shape with the previous routing and flipping per platform as
   each is measured.
4. **The two round-trip-preserved boxing sets** (`boxing_triton_gaps`, `boxing_cpp_ops`).
   For boxing platforms the generator reads the file it rewrites, so if either fails to
   recover a fact a working kernel is silently rerouted. The idempotency test catches a
   lossy round trip, but not a set that was already wrong in the input conf. Native vendors
   no longer have this exposure — `vendor_native_ops` now reads the generated `.inc` rather
   than parsing the conf back.
5. **The registration sets themselves.** `registered_impls()` parses `m.impl("op", ...)`
   out of the `.inc` files, which is a text scan of a generated artifact rather than
   something the compiler reports. A platform registering an op outside its `.inc` needs an
   explicit extra in the generator, or the op lands at `none` and a real kernel goes to
   `cpu_fallback`. I audited `register.cc` for this: the only conditional direct
   registrations are Ascend's `matmul`/`matmul_backward` (`register.cc:428-431`), which are
   carried as extras. The 22 unconditional ones at `register.cc:398-421` (`copy_`,
   `contiguous`, `clone`, `_to_copy`, `view`, `as_strided`, …) are hand-written structural
   kernels in `contiguous_ops.cc` and friends that call `at::native::flagos::<op>` with no
   backend-table lookup, and none of them appear in the op list, so no conf routes them
   either way. Worth a second pair of eyes on that conclusion, since it is the one place a
   text scan could disagree with the compiler.

### Questions for reviewer:

1. Land FlagGems-first routing for all native platforms now, or land the full-coverage
   shape with current routing and flip each platform as its hardware is measured?
2. Should `--check` run in CI to keep the confs from going stale? That is the mechanism
   that prevents the rot this PR fixes from recurring.
3. `mm` is deliberately excluded from the MetaX C++ set (`METAX_CPP_MEASURED` in the
   generator). The C550 shared-memory limit (65536 bytes) prevents the FlagGems C++ mm
   kernel from launching (requests 98304 bytes). `backends_metax.conf` routes it to `cuda`.
   If this has been remeasured on newer hardware, update `METAX_CPP_MEASURED` in
   `scripts/gen_vendor_confs.py` and regenerate.
